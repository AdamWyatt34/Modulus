# Full Scan — 2026-07-25 (post-2.1.0)

Deep read of all nine packages, the CLI/template layer, packaging/CI, and docs at HEAD (`29c03fd`), two releases after the July gap analysis. Method: six parallel area audits (mediator, messaging core, broker transports, generators/analyzers, CLI/templates, packaging/docs) with every candidate finding re-read against the full code path before reporting; the four criticals and the headline highs were then re-verified line-by-line a second time during synthesis. No .NET SDK was available in the audit environment, so everything here is static analysis — findings marked *confirmed* are verified by code reading; *likely* means the mechanism is verified but a runtime repro would be needed to be certain.

> Headline: the 2.0/2.1 wave genuinely fixed the July findings it claimed to fix (verified: inbox reservation, DLQ tooling, health checks, metrics, upgrade command, E2E local feed). The new top-severity problems cluster in one theme: **the paths nobody executes**. Scaffolds build but are never *run* (dead modules, red scaffolded tests), the outbox handles happy rows but not poison rows, and generated code compiles in the test project but not in a real Domain project. §"Fix order" at the end sequences the work; §"AI eval kit" explains why the strongest QA investment available is an execution-based harness.

## Critical

### C1. `Mediator.Publish` dispatches on the static generic type — domain events are silently dropped in every scaffolded app

`src/Modulus.Mediator/Mediator.cs:105-108`. `Send`/`Query`/`Stream` all dispatch on `GetType()` + `MakeGenericMethod`; `Publish<TEvent>` alone resolves `IDomainEventHandler<TEvent>` from the *compile-time* type. The canonical pattern — `foreach (var domainEvent in domainEvents) await _mediator.Publish(domainEvent, ct)` over a `List<IDomainEvent>` — infers `TEvent = IDomainEvent`, MS.DI has only closed registrations (generator emits `IDomainEventHandler<ConcreteEvent>`, `HandlerRegistrationGenerator.cs:307`), so **zero handlers resolve and the method returns successfully**. That exact loop ships in the scaffold template (`templates/init/building-blocks/infrastructure/Persistence/BaseDbContext.cs.template:70`), the sample (`samples/.../BaseDbContext.cs:64-72`), and the docs (`docs/mediator/domain-events.md:242-245`, whose "all registered handlers are resolved" claim is false for this flow). Tests only publish concrete types, which is why this was never caught. **Fix**: runtime-type dispatch in `Publish` (same `GetType()` pattern as `Send`); add a test that publishes through an `IDomainEvent`-typed variable.

### C2. `add-module` produces modules the host never loads — and docs say no wiring is needed

`src/Modulus.Cli/Handlers/AddModuleHandler.cs:107-122`. Module discovery is compile-time over the host's referenced assemblies (`ModuleRegistrationGenerator.cs:54` iterates `ReferencedAssemblySymbols`), but `add-module` only adds projects to the `.slnx` — it never adds a `ProjectReference` from `<Solution>.WebApi` to the module, and `WebApi.csproj.template` references only BuildingBlocks. Result: `modulus init EShop && modulus add-module Catalog && dotnet run` → `CatalogModule.ConfigureServices` never runs, endpoints 404, **silently** — the solution still builds, so the build-only E2E passes. The sample proves the manual fix (hand-added `Orders.Infrastructure`/`Notifications.Infrastructure` references in `SampleApp.WebApi.csproj:12-13`), while `docs/cli/add-module.md:80` claims "No manual composition root file needs to be updated" and the getting-started walkthrough curls endpoints that 404. **Fix**: `add-module` edits the host csproj (the CLI already does XML-parsed reference wiring in `AddConsumerHandler` — reuse it); `remove-module` must then also scan the host (see H-CLI1). Promote E2E from build-only to run-and-curl.

### C3. Poison outbox rows wedge the queue head and hot-spin the processor — invisible to all ops tooling

`src/Modulus.Messaging/Outbox/OutboxDispatcher.cs:76-97,145` + `OutboxProcessor.cs:33-37`. The two skip paths (unknown type, deserialize-failed) `continue` without marking the row processed or failed, so the row matches `GetPending` forever and — being oldest — sorts first. `EventType` is the **assembly-qualified name captured at save time** (`EfOutboxStore.cs:15`) compared ordinally against the *current* AQN, so a deploy that bumps assembly version (CI-stamped versions), renames an event, or omits an assembly from `options.Assemblies` turns every in-flight row into a permanent head-of-queue blocker. With ≥ `OutboxBatchSize` such rows: `DispatchPendingAsync` returns `pending.Count` (which counts skipped rows), `fetched >= OutboxBatchSize` short-circuits the wait → **tight loop, no delay, warning-log flood, zero dispatch of newer rows**. These rows never appear in `modulus outbox list-failed` (`EfOutboxAdminStore.GetFailedAsync` filters `Attempts >= maxAttempts`; these have `Attempts == 0`). **Fix**: mark skip-path rows failed/parked (a parked state visible to the admin store), use version-insensitive type identity for the allowlist, and return *dispatched* (not fetched) count from `DispatchPendingAsync`.

### C4. `[StronglyTypedId]` generates EF Core-dependent code unconditionally — uncompilable exactly where docs say to use it

`src/Modulus.Generators/StronglyTypedIdGenerator.cs:148` emits a nested `Microsoft.EntityFrameworkCore.Storage.ValueConversion.ValueConverter` in every generated ID. Any project without an EF Core reference gets CS0234 in generated code. IDs belong in Domain projects (`docs/generators/strongly-typed-ids.md` shows exactly that), Domain templates have no EF reference, and MOD004 exists to keep EF *out* of Domain. Compounding: scaffolded Domain projects don't reference `ModulusKit.Generators` at all (analyzer assets don't flow across `ProjectReference`), so the attribute silently generates nothing there; and the sample dodges the whole feature with a hand-written `StronglyTypedId<T>` base record (`samples/.../Identifiers/StronglyTypedId.cs`) — the flagship generator is not dogfooded. Tests mask it because the test project references EF (`Modulus.Generators.Tests.csproj:18`). **Fix**: gate the ValueConverter on `GetTypeByMetadataName("Microsoft.EntityFrameworkCore.DbContext") is not null` (the pattern `ModuleRegistrationGenerator.cs:22-24` already uses for ASP.NET Core), wire the Generators package into Domain templates, and dogfood it in the sample.

### C5. The shipped outbox is not transactional with business data — contradicting the package's core guarantee

`src/Modulus.Messaging/Outbox/EfOutboxStore.cs:8-28`. `EfOutboxStore` writes through its own `OutboxDbContext` (own connection) and commits immediately; there is no supported enlistment in the caller's business transaction. A crash between the business `SaveChangesAsync` and `outbox.Save` loses the event; the reverse order publishes a ghost event for a rolled-back business change — and `Save` calls `Notify()` immediately, putting the ghost on the wire within milliseconds. Docs claim the opposite (`docs/messaging/outbox-pattern.md:109-118` "uses your application's DbContext … same transaction"; `src/Modulus.Messaging/README.md:96` "within the same transaction as your business data") while the sample README quietly admits "two transactions" (`samples/SampleApp/README.md:110-113`). Severity is "critical" as a *promise* defect: this is the property the package is named for. **Fix options**: (a) document honestly and provide a supported same-DbContext story — map `OutboxMessage` into the consumer's context and let `AddModulusOutbox` accept a user context; (b) make `EfOutboxStore` accept the active `DbContext`/transaction. Note the interaction with H-MSG2 below: the doc-endorsed single-context path is exactly the one whose wake signal gets eaten.

## High

### Messaging core

- **H-MSG1 — Inbox idempotency keys on the handler's *simple* class name.** `src/Modulus.Messaging/Dispatch/HandlerInvoker.cs:28` uses `GetType().Name`. Two modules each defining `OrderPlacedHandler : IIntegrationEventHandler<OrderPlaced>` — the natural naming in this architecture — share one inbox key: the first marks `(EventId, "OrderPlacedHandler")` processed, the second is skipped forever and counted as `InboxDeduplicated`. Enabling the recommended inbox silently disables one module's handler. Fix: use `FullName`; migration note required (existing `InboxMessageConsumers.Name` rows).
- **H-MSG2 — 2.1.0 wake signal lost for saves under EF's implicit transaction.** `OutboxNotifyingInterceptor.cs:138-148`: a save with ≥2 commands gets an implicit relational transaction; `TransactionCommittedAsync` fires **before** `SavedChangesAsync`, `NotifyIfDeferred` sees `NotifyOnCommit == false` and `ClearAll`s the state, so the subsequent `NotifyOrDefer` finds nothing → no notify, row waits out the full poll interval. This is the canonical business-row+outbox-row save on a user-mapped context — the "milliseconds" headline silently degrades to seconds exactly where it matters. Tests cover only single-command and explicit-`BeginTransaction` saves. (*Likely* — interception order verified against EF Core semantics; needs a runtime repro test.) Fix: in `NotifyIfDeferred`, treat pending `HasNewOutboxRows` at commit time as notify-eligible, or defer eagerly when `context.Database.CurrentTransaction` is set during `SavingChanges`.
- **H-MSG3 — Outbox retry has no backoff; a broker outage hot-loops the processor.** `OutboxDispatcher.cs:58` reads only `RetryPolicy.MaxAttempts`; `InitialInterval`/`MaxInterval`/`IntervalIncrement` are dead config for the outbox (used only by consumer retry), despite `README.md:81` advertising independent exponential backoff. And because failed rows still count in the returned `pending.Count`, ≥ batch-size failing rows → `fetched >= OutboxBatchSize` → no wait → fetch/fail/mark 100 rows in a tight loop until `MaxAttempts` dead-letters the backlog. Fix: return dispatched count (shared with C3) and apply the configured backoff via a `NextAttemptAt` column or in-loop delay.
- **H-MSG4 — Dead-lettering never releases the inbox reservation → DLQ replay within 5 minutes re-dead-letters without executing.** `ConsumerDispatcher.cs:89-98,158-174` + `EfInboxStore.cs:107-117`: retries exhaust in ~53 s (1+6+16+30), the reservation stays fresh for `ConsumerReservationTimeout` (5 min default), so a prompt `modulus dlq replay` deterministically fails every attempt with `InboxReservationPendingException` and dead-letters again — zero handler executions. Fix: release (or stale-mark) the reservation on the dead-letter path.

### Transports

- **H-TR1 — Unsynchronized `HashSet` on the RabbitMQ publish hot path.** `RabbitMqTransport.cs:20,87-92`: `_declaredExchanges` `Contains`/`Add` race from concurrent publishes (singleton transport, called from request threads via `IMessageBus` plus the outbox loop). Undefined behavior when two first-publishes race. Fix: `ConcurrentDictionary<string, byte>` or lock. Same shape (lower stakes) for `_client ??=` lazy init in `AzureServiceBusTransport.cs:31,38-41`.
- **H-TR2 — Consumer death is invisible: health probes report healthy while consumption is permanently stopped.** RabbitMQ probe checks only `connection.IsOpen` (`RabbitMqTransport.cs:201-216`); channel-level errors are not auto-recovered by the client (queue deleted → `basic.cancel`; broker `consumer_timeout` exceeded by the ~53 s in-process retry budget → channel closed; 406 bad-ack). ASB probe never contacts the namespace at all (`AzureServiceBusTransport.cs:145-160` — `client.IsClosed` is only true after local disposal), and with `AutoProvision=false` a missing topic/subscription lets `StartProcessingAsync` succeed while `ProcessErrorAsync` loops forever (`:82-119`) — app green, zero consumption. Fix: register channel-shutdown/consumer-cancelled observers + restart consume channel; make the ASB probe do a real admin/receive call; fail fast on `MessagingEntityNotFound` at startup.
- **H-TR3 — RabbitMQ `StopConsumingAsync` doesn't drain in-flight handlers.** `RabbitMqTransport.cs:218-225`: `BasicCancelAsync` returns while up to prefetch-count dispatches (each possibly mid-retry-sleep) are still running; the host then disposes the ServiceProvider → `ObjectDisposedException` inside dispatch → counted as handler failure → guaranteed redeliveries every deploy, and a message on its final attempt can be spuriously dead-lettered. The in-memory and ASB transports both honor the drain, confirming intent. Fix: track in-flight dispatches and await them (bounded) before returning.

### Generators / analyzers

- **H-GEN1 — Duplicate hint name for same-named IDs.** `StronglyTypedIdGenerator.cs:98`: two `[StronglyTypedId]` structs with the same name in different namespaces of one assembly → `AddSource` duplicate-hintName exception → generator faults (CS8785), *all* IDs in the assembly lose their generated members.
- **H-GEN2 — Referenced-assembly handler scan ignores accessibility and struct-ness.** `HandlerRegistrationGenerator.cs:178-208`: an `internal` handler in a referenced module (the idiomatic shape) is emitted into the host's registrations → CS0122 in generated code; `record struct` handlers → CS0452 (contradicting the deliberate local-path struct exclusion at `:82-95`).
- **H-GEN3 — `AnalyzeCandidate` `return default` NREs the whole generator.** `HandlerRegistrationGenerator.cs:37,117`: default `CandidateResult.Registrations` is a default `ImmutableArray`; `.Where(r => r.Registrations.Length > 0)` throws, generator faults, **no registrations are generated at all**. Trigger includes legal partial-class shapes where `GetDeclaredSymbol` sees an abstract part.
- **H-GEN4 — MOD003 code fix produces non-compiling or invalid output.** `ExceptionThrowingInHandlerCodeFixProvider.cs:95-102`: in a non-async handler the emitted `return Error.X(...)` doesn't convert to `Task<Result>` (CS0029) — the shape in the project's own fix test, which only asserts text containment; for throw-*expressions* (`?? throw ...`, which the analyzer reports) the fix substitutes a statement node into an expression position → invalid tree/crash.
- **H-GEN5 — Every-keystroke full metadata walks.** `HandlerRegistrationGenerator.cs:44-45` and `ModuleRegistrationGenerator.cs:19-20,42-43` recursively walk every namespace of every referenced assembly (System.*, the whole closure) on each compilation change, ×3 generators; plus the handler pipeline's first stage captures `Diagnostic` (→ syntax tree) in a non-equatable model (`:31-34,348-357`), defeating incremental caching entirely. IDE-perf grade rather than correctness, but it affects every consuming solution constantly.

## Missing features

**New, not on any tracked backlog (ranked):**

1. **Outbox/inbox retention & cleanup** — processed rows accumulate forever; no purge job, TTL, or bulk API (`PurgeAsync` is one-row-by-id). Every peer (MassTransit, CAP, Wolverine, NServiceBus) ages out delivered rows. Unbounded growth eventually degrades `GetPending`/`TryReserve`.
2. **Multi-instance outbox competition** (`SKIP LOCKED`/lease/claim) — scaled-out hosts are the norm for the target audience; today replicas duplicate publishes and race `Attempts`.
3. **Trace-context propagation across the broker** — `TransportEnvelope` has no headers bag, no `traceparent`; producer Activity exists but consumer side creates none. End-to-end distributed tracing is impossible — a gap for a kit that advertises observability.
4. **Broker-native delayed redelivery** — consumer retry is in-process `Task.Delay` pinning a concurrency slot ~53 s per failing message (10 failing messages stall a RabbitMQ endpoint); backoff is lost on crash. RabbitMQ TTL/DLX-cycle or ASB `ScheduledEnqueueTime` makes it durable and non-blocking. Scheduled/delayed *publish* is the same missing primitive surfaced to users.
5. **Multi-targeting (net8.0/net9.0)** — net10.0-only excludes every LTS shop; likely the single biggest adoption filter (`Directory.Build.props:4`).
6. **Result combinators** — `Bind`/`Map`/`Tap`/`Ensure`/async `Match`/`FirstError`; today handler chaining is nested `if (r.IsFailure)` boilerplate and docs resort to `Errors.First()`.
7. **Host wiring + run-grade E2E for the CLI** — the fix for C2 plus E2E that *runs* the scaffold and its tests (would have caught C2, H-CLI2/4, and the Aspire injection no-op).
8. **Strongly-typed ID completeness** — string backing type, `IParsable`/`TryParse` (+`BindAsync`) so IDs work as minimal-API route parameters (today they can't), `IComparable<T>`, STJ dictionary-key support, EF bulk converter registration helper.
9. **Package hygiene guards** — `EnablePackageValidation` + PublicApiAnalyzers baselines (nine coordinated packages with a breaking-change history and no mechanical guard), Dependabot/Renovate, CodeQL, NuGet trusted publishing instead of a long-lived API key.
10. **`ModulusKit.Testing` package** — module test harness (fake transport, outbox/inbox assertion helpers — the in-memory transport is `internal`); "module-level integration testing" is a core pitch currently backed by raw boilerplate.
11. **Module DB migration story** — per-module DbContexts are scaffolded with no migrations workflow (`modulus add-migration`, EF `Design` reference, docs page); only the messaging contexts get `UseModulusMessagingMigrationsAsync`.
12. **CLI ergonomics** — `--dry-run` on all mutating commands (only `remove-module`/`upgrade` have it), generic types in `--result-type`/`--properties` (`List<T>` is rejected — the bread-and-butter query shape), route-param binding in `add-endpoint`, `--no-restore`, CI workflow + Dockerfile scaffolds, `dotnet new` template package for discoverability.
13. **Inbox recovery loop or API removal** — `IInboxStore.GetPending`/`MarkAsProcessed`/`ProcessedOnUtc` are dead surface: nothing calls them. Ship the reprocessor the schema implies, or delete.
14. **Mediator odds and ends** — cancellation token on `RequestHandlerDelegate` (timeout behaviors are impossible today), publish strategies (parallel/stop-on-first-failure), per-request exception→Error mapping, closed-generic/lifetime-controlled behavior registration, duplicate-handler diagnostics, stream pipeline (or at least a doc warning that stream validators silently never run).

**Already tracked** (in `missing-features-plan.md`, unchanged status): ASB emulator CI promotion, Codecov token, `rename-module`, BenchmarkDotNet baseline, broker fault-injection tests, `--json` on scaffolders. **Deliberately out of scope** (respected, not re-litigated): sagas-as-framework, point-to-point send, GraphQL/gRPC, provider-specific migrations.

## Test coverage gaps (the pattern behind the criticals)

Every critical shares one root cause: **nothing executes the artifacts end-to-end.**

- E2E builds scaffolds but never runs them (C2 invisible) and never runs the scaffolded tests (H-CLI4 invisible); `add-entity`/`add-command`/`add-query`/`add-endpoint` aren't in E2E at all — exactly where the compile-breaking generators live.
- Mediator tests never publish via an interface-typed variable (C1) and have zero cancellation tests.
- Generator tests all reference EF Core (C4 masked); no incrementality tests, no global-namespace/nested/internal/same-name cases; analyzer test helper filters out AD0001 crash diagnostics, so a crashing analyzer passes every "no diagnostic" test vacuously.
- Messaging tests cover the single-row skip but not skip-row starvation (C3), not the implicit-transaction save (H-MSG2), not same-named handlers (H-MSG1), not two competing dispatchers, not replay-vs-live-reservation timing (H-MSG4).
- Transport integration suites lack broker-restart, concurrent-publish (would likely expose H-TR1), shutdown-drain, and health-probe tests; the ASB suite runs only `AutoProvision=false`, so the entire provisioning path has zero coverage; both DLQ browsers have zero tests.

## AI eval kit — assessment

**As a general-purpose LLM-eval NuGet package inside ModulusKit: no.** Three structural reasons: (1) it's a different product for a different audience — nothing in the current surface touches LLMs, and "modular monolith toolkit" is a crisp identity worth protecting; (2) the coordinated one-version release scheme (scaffolded `Directory.Packages.props` pins all `ModulusKit.*` together) would chain a fast-moving AI package to nine stable infra packages; (3) .NET already has a first-party answer — `Microsoft.Extensions.AI.Evaluation` (evaluators, response caching, CI reporting) — so a me-too kit starts behind with no moat.

**But the instinct is right — aimed at a different target.** The highest-leverage version of "eval kit" for this repo is **execution-based agent evals for the toolkit itself**, and this audit is the evidence: every critical lived on a path that builds but is never *run*. Three concrete shapes, in order of value:

1. **Scaffold-exercise harness (CI)** — a task suite that actually drives the product the way a user (human or agent) would: `init` → `add-module` → `add-entity/command/query/endpoint/event/consumer` → `dotnet run` → curl endpoints → `dotnet test` → `doctor --strict`. Score = compiles + runs + responds + tests green + analyzers clean. This catches C2, H-CLI2/3/4, the Aspire injection no-op, and the red scaffolded tests *by construction*. It's the same harness whether a script or an agent drives it.
2. **Agent evals on top** — same task suite, but an AI agent (given the repo's existing `.claude/skills/moduluskit` skill and docs) performs realistic feature tasks ("add an Orders module with an OrderPlaced event consumed by Notifications"). Grade with compile/run/doctor/MOD-analyzer/test outcomes — objective, no LLM-judge needed. This doubles as (a) regression testing for the skill/docs against each release (the skill was just refreshed for 2.x — nothing verifies it), and (b) marketing evidence for an explicitly agent-friendly toolkit ("agents complete X% of Modulus tasks unaided").
3. **Agent-readiness as a product feature** — `modulus init` should emit an `AGENTS.md`/`CLAUDE.md` describing module boundaries, MOD rules, Result conventions, and CLI verbs (scaffolds currently ship none), and optionally install the moduluskit skill. The analyzers/doctor/`--json` surfaces already make the kit unusually agent-legible; finishing that story is on-brand differentiation that costs little.

If the ambition really is evals for *LLM features in apps*: build it as a separate package family/repo (not `ModulusKit.*`), on top of `Microsoft.Extensions.AI` abstractions, and integrate with Modulus only via an optional module template (e.g. `modulus add-module --template ai` scaffolding an eval test project). That keeps both products honest.
